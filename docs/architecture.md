# 系統架構與設計決策

**版本**：v2（2026-07-18 定案）｜**範圍**：平安聯合診所 照片與檢驗報告歸檔系統

## 1. 目標

1. 同仁用自己的手機幫病人拍照（病灶、傷口、文件），照片自動歸檔到正確病人名下，且**不留在私人手機**。
2. 檢驗所透過 LINE 傳來的檢驗報告影像，在**地端** OCR 讀出身分證字號等欄位後自動歸檔。
3. 同一位病人的所有紀錄（照片＋報告）整合在同一個資料夾，日後可依時間軸查閱。
4. 資料主權留在診所：**照片與報告的處理、儲存、查閱全在地端，不經網路上傳、不上任何雲端**；檢驗報告的傳入沿用既有 LINE 管道（本來就經過 LINE 的基礎設施）。唯一離開診所的實體是 3-2-1 備份中的**加密災難備援碟**（離地保存、雙人保管金鑰，見第 8 節）。

## 3. 元件分工

| 元件 | 來源 | 職責 |
|---|---|---|
| ClinicSnap | 開源（leon80148），用現成 Windows release，不改碼 | 手機掃 QR 拍照上傳、健保卡本機 OCR、照片落地資料夾 |
| 整合層 | 自建（Python 單一服務） | watcher、報告 OCR、身份解析、自動分類、歸檔搬移、SQLite 索引、待確認佇列、時間軸網頁 |
| 儲存 | 診所伺服器本機磁碟＋NAS 備份 | `archive\{證號}\` 人類可讀結構＋`clinic.db` 索引 |

部署拓撲：**單一伺服器**（診所裡常開機、接有線、磁碟大、設固定 IP 的那台 Windows 電腦）同時跑 ClinicSnap 與整合層；其餘電腦不裝任何東西。ClinicSnap 的通行碼（token）持久化於 config.json、重開機不變；IP 固定後 QR code 恆定，可印出貼在護理站。手機掃一次加入主畫面即可日常使用。

## 4. 身份解析（核心設計）

- **主鍵＝身分證字號**：它是唯一在照片端（健保卡 OCR）與報告端（報告文字）都天然存在的鍵。資料夾與索引都用證號。
- **HIS 病歷號＝選配別名**：拿得到就回填（資料夾自動改名），拿不到系統照樣完整運作。對照資料可來自：報告上印的病歷號、HIS 當日掛號名單匯出、健保卡 OCR（卡面含姓名＋出生日期＋證號）、佇列人工補登。
- **三層防呆**：
  1. 台灣身分證字號 checksum（內政部加權演算法）——可攔下**絕大多數**單碼誤讀，但並非全部：權重×誤差 ≡ 0（mod 10）的組合（如權重 5 的位數誤差 2）會通過檢查碼，因此 checksum 只是第一層，不得單獨作為歸檔依據；
  2. 生日交叉核對——對**已建檔病人**（patients 表內有生日資料者）為強制條件，證號＋生日皆吻合才可自動歸檔；
  3. **首見證號一律進待確認佇列**人工確認建檔——自動歸檔只適用於已建檔病人。此規則同時堵住「OCR 誤讀恰好產生另一個有效證號」與「有效但不存在的證號自動開新資料夾」兩種事故。任何一層存疑 → 佇列，**絕不猜**。

**自動歸檔判準（單一定義，全文件其他位置一律引用本節，不得另寫簡化版）**——同時滿足才可自動歸檔，其餘一律進佇列：
1. 批內恰好一個證號（恰一原則）——在**格式層**計數：任何形如 `[A-Z][0-9]{9}` 的候選都算一個，**未通過檢查碼的也算**，不得先濾掉再數（否則「兩位病人同框、其中一位證號被誤讀一碼」會被當成恰一而歸給另一位）；代價是報告上長得像證號的檢體／報告編號會讓該份報告進佇列，這是刻意的 fail-closed；
2. 該證號通過 checksum；
3. 該證號已存在於 patients 表（已建檔病人）；
4. **獨立第二驗證**（單靠 checksum＋已建檔仍可能誤中另一位已建檔病人，故必須再過一道與 OCR 無關的驗證）：
   - 檢驗報告：報告上的生日必須與建檔資料吻合（報告必有生日，必查）；
   - 照片批：N0 卡面生日讀得出 → 必須吻合；讀不出 → 伺服器複掃出的證號必須**等於手機端人工核對後帶入的病患代碼**（ClinicSnap 的「是，帶入」確認即人工背書），**且該證號須出自卡片影像**——文件照上的證號文字不得作為身份證據；
   - 兩者皆缺（生日不可讀且手機端未帶代碼）→ **fail closed，整批進佇列**。

**無證號病人的鍵空間**：未入籍新生兒等無證號者，由佇列人工建檔時配發內部暫時代號，格式 `P-{7 位流水號}`（含連字號，結構上永不與身分證格式 `[A-Z][0-9]{9}` 相符，不可能衝突）；資料夾即以暫時代號命名。日後取得證號 → 佇列「併檔」動作：資料夾更名、patients 表寫入別名對照、全程入稽核。手動輸入欄位的判讀規則：輸入符合證號格式且 checksum 通過 → 視為證號；其他字串 → 視為病歷號別名查表解析；解析不到 → 佇列。

流程圖與各節提到的「閘門」都指這一組完整判準。新病人第一批必然走一次佇列（人工確認建檔），之後即可自動歸檔——這是刻意的一次性成本。
- 外籍人士：新式統一證號（1 字母＋9 碼）同格式同 checksum 直接支援；舊式（2 字母）格式可辨識但無 checksum，一律進佇列人工核對。無證號者（如未入籍新生兒）流程見上方「無證號病人的鍵空間」。

## 5. 病灶拍照「N0 錨定協定」

1. **5.1 N0 起手式**：每一批的第一張＝健保卡＋病灶同框（臨床攝影「腕帶入鏡」傳統的診所版，attribution 證據在照片裡）。
2. **5.2 N1–Nn**：後續連拍病灶特寫，卡片**不得**再入鏡（第二張以後出現任何卡片影像即整批進佇列，見 5.6）。
3. **5.3 確認送出＝完成一批**；手機端顯示辨識結果供核對。
4. **5.4 伺服器複掃整批**：整批通過第 4 節的**自動歸檔判準**→ 自動歸檔；其餘一律整批進佇列。
5. **5.5 批次即邊界**：身份只在一批之內生效、跨批絕不繼承；換病人＝重新 N0。
6. **5.6 多卡即人工**：伺服器複掃時，批內第二張（含以後）出現任何卡片影像＝未遵循 N0 首張協定或兩位病人混批——即使首張卡驗證全數通過也一律進佇列，不自動歸檔。
7. **5.7 批次還原機制（本節第 7 條；整合層實作規格，fail-closed）**：ClinicSnap 逐檔寫入、無批次 manifest，整合層以檔名特性重組批次並以下列**確定性規則**擋掉所有可疑組——寧可進佇列，絕不誤併：
   - **分組鍵**：同一上傳請求的所有檔案共用同一時間戳（上游一請求取一次 `now`），故以（病患代碼, 日期＋時分秒）分組；
   - **靜置窗**：組內最新檔案落地超過 N 秒（預設 10）才進入判定，避免處理寫入中的半批；
   - **完整性檢查（確定性）**：單一乾淨批的檔名序號必為 1..N 連續且無碰撞後綴（上游同名碰撞會產生 `-2`、`-3` 後綴）。序號不連續、重複、或出現碰撞後綴＝兩批同鍵混併的確定證據 → 整組進佇列；
   - **遲到檔防線**：已處理批的分組鍵若再出現新檔（慢速寫入的尾檔），確定性可偵測（鍵相同）→ 該檔進佇列人工併回，**絕不**當成新批自動歸檔；
   - **殘餘風險誠實聲明**：以上規則保證「不誤併、不誤歸」，但無法證明「批已收齊」（上游無總數訊號）——尾檔最壞情況是晚一步經佇列人工併回，不會遺失也不會歸錯人。長期解法是向上游提議批次 manifest（已列 v1 待辦）。

**5.8 卡片影像的處置（v0 實況）**：偵測到健保卡的影像**一律先歸檔為「病灶照」並建立
`card_suspect` 佇列項**，由管理者二選一：保留（卡＋病灶同框的 N0，檔案與紀錄不動）或
移除（純卡片照移至 `trash/`，可回收、非永久刪除）。**v0 不自動刪除任何影像**——自動刪
與 fail-closed 鐵律相衝（誤判即永久失去 attribution 證據），因此把裁決權留給人。
「純卡片照用畢即刪」是未來階段的目標形態，非目前行為。

## 6. 歸類模式

三個維度：**病人**（證號＝主資料夾）×**日期**（檔名開頭）×**類型**（檔名標籤＋資料庫 tag）。

```
archive\{身分證號}\{YYYY-MM-DD}_{類型}_{序號}.jpg
例：archive\A12345****\2026-07-18_病灶照_02.jpg      ← 後四碼遮罩之格式示意，非真實證號
```

| 大類 | 子類 | 判定方式 | 階段 |
|---|---|---|---|
| 臨床照片 | 病灶、傷口（部位標籤日後加） | 來源＝手機拍照 | v0 |
| 檢驗報告 | CBC、生化、尿液、過敏原 | 來源＝inbox＋OCR 關鍵字規則（`extract.classify_report`） | v0（含子類） |
| 其他報告 | InBody（體脂）；睡眠檢測等待擴充 | 關鍵字規則 | InBody v0；其餘 v1 |
| 外院與轉診文件 | — | 規則對不上 → 歸「文件」或佇列人工標 | v0 |
| 識別影像 | 健保卡 | v0 不自動刪：一律歸檔為病灶照＋建 `card_suspect` 佇列，管理者裁決保留／移至 trash（見 §5 的 5.8） | v0 |
| 歷史回溯資料 | 依檢驗所交付格式 | 影像/PDF 走同管線；CSV 直接對映 | v2 |

檔案狀態流：進站 → 解析・驗證・分類 → 自動歸檔｜待確認 → 已確認。改派：v0 僅限**仍在待確認佇列**的項目可於網頁指派；已歸檔紀錄的改派／併檔為 v1 網頁功能，v0 僅程式 API（見 §11）。SQLite 只是索引與稽核，**資料夾本身就是可獨立使用的備份格式**。

## 7. 檢驗報告接收（LINE）

- **v0**：檢驗所照常傳 LINE 群組，同仁在電腦 LINE 把影像拖進 `inbox\`，其餘全自動。
- **v1（全自動）**：開一個**專用免費 LINE OA**（不掛診所既有 OA），啟用「允許加入群組」，拉進檢驗所群組潛水；群組任何影像訊息觸發 webhook → 驗 X-Line-Signature → Content API 下載 → 落 `inbox\`。webhook 端點二選一：Cloudflare named tunnel 直達診所伺服器（推薦，零第三方落地，需網域掛 Cloudflare）或雲端短暫中繼。開啟 webhook redelivery、收到即下載（LINE 內容有保存期限）。
- 前提：該群組須為一般 LINE 群組（OpenChat 不支援 bot）。

## 8. 法遵與隱私

- 病歷保存：醫療法第 70 條至少 7 年；**未成年病人保存至成年後 7 年**——實際年限依建檔年齡而異（新生兒建檔約需保存 25 年、17 歲建檔約 8 年），備份與媒體壽命設計一律取最長情境（數十年）為準。
- 伺服器全碟加密＋歸檔資料夾 ACL 最小權限；歸檔區不進任何雲端同步。
- **網路傳輸安全（誠實聲明＋控制）**：上游 ClinicSnap 目前以區網明文 HTTP 傳輸（token 帶在 QR 網址、影像不經 TLS）——威脅模型是「已連上員工 Wi-Fi 的（被入侵）裝置」，因此光靠共用 PSK 的專屬 VLAN 不足以自保。v0 必要控制（缺一則將 TLS 提前到 v0）：①員工 SSID 啟用 **WPA3-SAE**（每裝置獨立金鑰，阻斷同網被動解密；設備不支援＝控制不成立）；②**AP client isolation**（無線裝置互不可達，僅可達有線伺服器——部署日必須實測「手機→有線伺服器可通、手機→手機不通」，部分低階 AP 會連有線側一併隔離，驗證失敗＝控制不成立）；③防火牆/ACL 限制員工 SSID 只能連伺服器 IP 的服務埠；④伺服器走有線、QR 紙本僅張貼於員工區。**上述任一項在現場設備上做不到，就把 TLS 反向代理（自簽 CA 佈到員工手機）從 v1 提前到 v0**，不得帶著已知不成立的控制上線。v1 仍列：向上游提議原生 HTTPS。本文件的隱私保證以「以上控制實測通過」為前提，不宣稱傳輸層加密。
- **應用層存取控制（整合層 Web 介面規格）**：時間軸與佇列介面必須登入才可用——每位同仁個人帳號（密碼雜湊儲存）、session 管理、兩種角色（一般＝查閱；管理＝佇列裁決與指派；已歸檔紀錄的改派／併檔網頁介面為 v1，v0 僅程式 API）；`audit_logs` 的「誰」一律綁登入帳號，禁止共用帳號。表單一律帶 session 綁定的 CSRF token 驗證。
- **整合層網頁的網路暴露（誠實聲明）**：整合層以 `web_host=0.0.0.0` 監聽 8770 埠，也就是**綁在這台伺服器的所有網路介面上**，程式本身不做來源 IP 過濾。「不對外開放」是由**主機防火牆規則**達成的——部署時只開 `profile=private,domain` 的 8756／8770 入站規則（見 `deploy/AGENT_DEPLOY.md`）。因此：①這台機器的網路連線設定檔（`Get-NetConnectionProfile`）若被 Windows 歸類成 **Public**，該規則不生效，必須先改回 Private 再繼續，**不得**改用 `profile=any` 繞過去；②這台機器不得同時接上對外可路由的網段。此控制未通過實測前，不得宣稱介面「僅限內網」。
- **整合層登入亦為區網明文 HTTP（誠實聲明）**：整合層網頁沒有 TLS，帳號密碼與病人影像同樣以明文在區網傳輸——與上游 ClinicSnap **同一個威脅模型**（已連上員工 Wi-Fi 的被入侵裝置），因此完全受本節上一項的網段控制與「任一控制不成立就把 TLS 反向代理從 v1 提前到 v0」規則涵蓋。TLS 提前時，兩個服務要一起納入，不得只包 ClinicSnap。
- **備份（3-2-1 原則，對齊數十年保存需求）**：至少 3 份（本機＋NAS＋離地輪替碟）、2 種媒體、1 份離地；NAS 快照或不可變備份防勒索；備份全加密，金鑰以雙人保管的離線方式留存（金鑰遺失＝資料滅失，視同資安事件演練項目）；每年至少一次還原演練與媒體健康檢查、按媒體壽命汰換。
- 稽核（範圍誠實聲明）：`audit_logs` 涵蓋**經由系統介面**的以下動作（誰、何時、對誰、做了什麼）：登入與登入失敗、病人時間軸查閱（`view_timeline`）、單一檔案查閱與佇列縮圖查閱（皆記 `view_file`）、自動歸檔（`auto_file`）、佇列裁決與其失敗（`resolve`／`resolve_error`）、卡片保留與移除（`card_keep`／`delete_card`）、建立病人與帳號、併檔（`merge`）、改鍵（`reassign`）、CSRF 拒絕（`csrf_reject`）。**未涵蓋**：病人清單搜尋等純瀏覽頁面，以及一切不經網頁介面的操作。直接開資料夾（檔案總管）屬管理者救援通道，不經應用層稽核——因此 archive 目錄 ACL 僅開放服務帳號與極少數管理者，並建議開啟 Windows 物件存取稽核（SACL）補齊這一段的紀錄。
- 同意與守則：門診同意書增列臨床攝影條款；員工 AI 使用守則增補「只准用系統拍、不得用相機 App、不得截圖外傳」。技術上手機網頁拍照不寫入手機相簿，已從架構面擋掉大部分 BYOD 風險。
- 院內政策：ClinicSnap 的網際網路（tunnel）模式不啟用，維持照片零出診所。

## 10. 關鍵決策記錄

| 決策 | 選擇 | 理由 |
|---|---|---|
| 拍照端 | 用 ClinicSnap 現成 release，不 fork | 需求重疊八成、工程品質經逐檔審閱；上游無 LICENSE，改作需先取得授權 |
| 部署 | 全地端單一伺服器 | 病灶照與報告無法去識別化，上雲即完整個資出門；診所量體地端綽綽有餘 |
| OCR | RapidOCR（PP-OCR、ONNX、純 CPU） | 與 ClinicSnap 同棧；實測歸檔關鍵欄位抽取率足夠（見 bench）；無需 GPU |
| 主鍵 | 身分證字號（HIS 病歷號降為選配） | 照片端與報告端唯一共同鍵；HIS 對照取得與否不再阻斷專案 |
| 歸錯人防線 | N0 協定＋批次邊界＋完整歸檔判準（§4）＋佇列 | 歸錯人是本系統最嚴重事故，流程與多重驗證並用 |
| 報告接收 | v0 人工拖入、v1 webhook | 先讓價值落地，再自動化「拖」這一步；下游管線共用 |
